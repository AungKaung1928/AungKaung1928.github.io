Panda Pick-and-Place Pipeline

A ROS 2 Humble workspace in which a Franka Panda clears seven red balls into a box using only what a simulated camera saw. An OpenCV node finds the balls, a C++ node drops what the arm cannot reach, and a state machine grasps only what survived — 7 of 7 placed, on mock hardware.

ROS 2 Humbleのワークスペースで、Franka Pandaが模擬カメラの見たものだけを頼りに赤いボール7個を箱へ片付けます。OpenCVのnodeがボールを検出し、C++のnodeが届かない対象を除外し、state machineは残ったものだけを掴みます（mock hardware上で7個中7個を配置）。

01

In plain words概要

What the system does, and the one design choice that makes it more than a scripted animation.

システムが何をするのか、そして単なる台本通りのアニメーションで終わらせないための設計判断です。

Imagine a robot arm bolted to a table. Seven red balls are scattered in front of it and there is an orange box off to one side. The job is: pick up every ball and put it in the box, without a human telling the arm where anything is.

テーブルに固定されたロボットアームを想像してください。目の前に赤いボールが7個散らばり、横にはオレンジ色の箱があります。 課題は、どこに何があるかを人がアームに教えることなく、すべてのボールを拾って箱に入れることです。

The naive way to build this is to write the seven ball positions into the code and command the arm to those coordinates. That would work, and it would prove nothing — the arm would perform the same dance whether the balls were there or not. This project deliberately does not do that.

素朴な作り方は、7個のボールの位置をコードに書き込み、その座標へアームを動かすことです。それでも動きはしますが、何の証明にもなりません。 ボールがあってもなくても、アームは同じ動きを繰り返すだけだからです。このプロジェクトでは、あえてその方法を取っていません。

Instead the positions travel a full loop. A fake camera draws a picture of the table. A separate program looks at that picture, finds the red blobs, and converts pixel coordinates back into metres. A third program (written in C++) checks whether the arm's joints can physically reach each of those metre coordinates and drops the ones that fail. Only what comes out of the far end of that chain is ever grasped. The arm literally does not know where the balls "really" are.

代わりに、位置情報はループを一周します。疑似カメラがテーブルの画像を描画します。別のプログラムがその画像から赤い領域を見つけ、 ピクセル座標をメートル単位に変換します。3つ目のプログラム（C++製）が、アームの関節でその各座標に物理的に届くかを確認し、届かないものを除外します。 掴む対象は、この流れの最後まで残ったものだけです。アームはボールの「本当の」位置を文字どおり知りません。

The one sentence that describes the architectureアーキテクチャを一文で表すと

Perception drives motion — the ground-truth ball positions exist only to draw the picture, and the state machine subscribes to the validator's output, never to the truth.

認識が動作を決めます。ボールの真の位置は画像を描くためだけに存在し、state machineがsubscribeするのはvalidatorの出力であって、真値ではありません。

Why a "fake" camera counts「偽物」のカメラでも意味がある理由

The camera node is not a real driver, it is an OpenCV drawing routine: grey background, grid lines, an orange rectangle for the box, red filled circles for the balls. But it publishes on the exact same ROS 2 topic type a real camera driver uses (sensor_msgs/Image) with real intrinsics on /camera/camera_info. So every node downstream of it is the code you would ship. Replacing the simulator with a RealSense driver means changing one line in the launch file and nothing else.

カメラnodeは実際のドライバではなく、OpenCVの描画処理です。灰色の背景、グリッド線、箱を表すオレンジの矩形、ボールを表す赤い塗りつぶし円を描きます。 ただし、実カメラのドライバと全く同じROS 2のtopic型（sensor_msgs/Image）でpublishし、/camera/camera_infoには実際の内部パラメータを流します。 そのため、下流のnodeはすべて、そのまま製品に載せられるコードです。シミュレータをRealSenseドライバに置き換える場合も、launchファイルを1行変えるだけで済みます。

What this does not give you is robustness. There is no sensor noise, no motion blur, no lighting variation, no shadow. Detection here is HSV thresholding on a synthetic frame — it works perfectly because the image is perfect. That limitation is stated in the repository's own README rather than glossed over, and it is worth repeating here.

一方で、ロバスト性は得られません。センサーノイズも、モーションブラーも、照明の変化も、影もありません。 ここでの検出は合成画像に対するHSVの閾値処理であり、画像が完璧だから完璧に動いているだけです。この制約はリポジトリのREADME自体にごまかさずに書かれており、ここでも改めて明記しておきます。

The loop that closes閉じるループ

When a ball is grasped, the state machine publishes remove:ball_3 on /scene_object_updates. The camera simulator receives that and stops drawing ball 3. On the next frame the detector sees six balls instead of seven, the validator forwards six, and the state machine has one fewer target. That is what makes it a loop rather than a list — the picture changes because the arm acted on it.

ボールを掴むと、state machineが/scene_object_updatesにremove:ball_3をpublishします。 カメラシミュレータはそれを受け取り、ボール3の描画をやめます。次のフレームでは検出器が7個ではなく6個を検出し、validatorも6個を転送し、state machineの対象が1つ減ります。 アームが動いた結果として画像が変わる。これが、単なるリストではなくループである理由です。

The vision half, step by step画像処理側の詳細

From a drawn image to a metre coordinate — HSV masking, contour filtering, and the pinhole back-projection.

描画された画像からメートル座標まで。HSVマスク、輪郭のフィルタリング、ピンホールモデルによるback-projectionです。

Why red is detected with two hue ranges, not one赤の検出に色相範囲を2つ使う理由

HSV separates colour (hue) from brightness and vividness, which is why it is used for colour thresholding instead of raw RGB — a red ball in shadow and the same ball in light have very different RGB values but nearly the same hue. OpenCV stores hue as 0–179. Red sits at the seam: pure red is hue 0, and slightly-purple red is hue 179. A single window [0, 10] would miss half of it. So the node builds two masks and ORs them together:

HSVは色（色相）を明るさや鮮やかさから分離します。そのため、色の閾値処理には生のRGBではなくHSVを使います。影の中の赤いボールと光の当たった同じボールでは、RGB値は大きく違っても色相はほぼ同じだからです。 OpenCVは色相を0〜179で表します。赤はその継ぎ目にあり、純粋な赤は色相0、やや紫寄りの赤は色相179です。[0, 10]の1範囲だけでは半分を取りこぼします。そこでnodeは2つのマスクを作り、ORで結合します。

hsv_red_lo1: [0,   120, 80]     hsv_red_hi1: [10,  255, 255]
hsv_red_lo2: [170, 120, 80]     hsv_red_hi2: [180, 255, 255]

The second and third numbers matter as much as the hue: saturation ≥ 120 excludes washed-out greys that happen to lean red, and value ≥ 80 excludes near-black pixels where hue is meaningless noise.

2番目と3番目の値も色相と同じくらい重要です。彩度 ≥ 120は、たまたま赤寄りになった色あせた灰色を除外し、明度 ≥ 80は、色相が意味のないノイズになる黒に近いピクセルを除外します。

Open, then closeopenしてからclose

The raw mask is noisy at the edges. Two morphological operations clean it with a 7×7 elliptical kernel:

生のマスクは境界付近にノイズがあります。7×7の楕円カーネルを使った2つのモルフォロジー演算で整えます。

MORPH_OPEN
Erode then dilate. Removes isolated specks smaller than the kernel without shrinking the real blobs.
収縮してから膨張。本物の領域を縮めずに、カーネルより小さい孤立したノイズを取り除きます。
MORPH_CLOSE
Dilate then erode. Fills small holes inside a blob — such as the white outline stroke drawn around each rendered ball.
膨張してから収縮。描画された各ボールの周りの白い輪郭線のような、領域内部の小さな穴を埋めます。

Order matters. Closing first would fuse two nearby specks into one fake object before opening had a chance to delete them.

順序が重要です。先にcloseすると、openで消す前に、近くにある2つのノイズが1つの偽物体に融合してしまいます。

Centroid from image moments, not from the bounding box重心はbounding boxではなく画像モーメントから

Once a contour survives the 400 px² area filter, the centre is computed from moments: u = m10/m00, v = m01/m00. That is the area-weighted average pixel position — a sub-pixel value, and it is robust to a ragged edge in a way that the centre of a bounding rectangle is not. For a circular ball the difference is small; for a partly-clipped blob it is not.

400 px²の面積フィルタを通過した輪郭は、モーメントから中心を計算します（u = m10/m00、v = m01/m00）。 これは面積で重み付けしたピクセル位置の平均で、サブピクセル精度の値になります。外接矩形の中心と違い、ギザギザした境界にも強い手法です。 円形のボールでは差は小さいものの、一部が欠けた領域では大きな差になります。

Back-projection, and where the intrinsics come fromback-projectionと内部パラメータの出どころ

The two lines that turn pixels into metres are, in the code:

ピクセルをメートルに変換する2行は、コード上では次のとおりです。

wy = cam_y + (u - cx) * cam_h / fx
wx = cam_x - (v - cy) * cam_h / fy
wz = 0.0        # DETECT_Z — the table plane assumption

Note the sign flip and the axis swap. Image u grows to the right and maps to the robot's y; image v grows downward and maps to the robot's x with a minus sign. Getting this wrong produces a system that runs cleanly and reaches for the mirror image of every ball, which is exactly the class of bug that never raises an exception.

符号の反転と軸の入れ替えに注意してください。画像のuは右方向に増え、ロボットのyに対応します。画像のvは下方向に増え、マイナス符号付きでロボットのxに対応します。 ここを間違えると、システムはエラーなく動いたまま、すべてのボールの鏡像の位置へ手を伸ばします。まさに例外が一切出ない種類のバグです。

The detector starts with hard-coded defaults for fx, fy, cx, cy but overwrites them the moment a CameraInfo message arrives on /camera/camera_info. That is how a real driver publishes calibration, so the node reads it the way it would read a real one. Only the extrinsics — where the camera is mounted — come from the YAML, and they are shared with the simulator so both ends agree by construction.

検出器はfx, fy, cx, cyのハードコードされた初期値で起動しますが、/camera/camera_infoにCameraInfoメッセージが届いた時点で上書きします。 実際のドライバもこの方法でcalibrationをpublishするため、nodeは実機と同じやり方で読み込みます。YAMLから読むのはカメラの取り付け位置である外部パラメータだけで、これはシミュレータと共有しているため、両者は構造的に一致します。

Why cv_bridge was replaced by 40 linescv_bridgeを40行のコードに置き換えた理由

cv_bridge is the standard ROS library for converting between OpenCV arrays and sensor_msgs/Image. It exists to handle roughly twenty pixel encodings from C++, and it ships as a compiled extension linked against a specific NumPy major version. In this package both ends of the image path are internal and both are bgr8, so the conversion is a reshape and a copy.

cv_bridgeは、OpenCVの配列とsensor_msgs/Imageを相互変換するROSの標準ライブラリです。C++から約20種類のピクセルエンコーディングを扱うためのもので、特定のNumPyメジャーバージョンにリンクしたコンパイル済み拡張として配布されています。 このパッケージでは画像経路の両端がどちらも内部実装で、どちらもbgr8なので、変換はreshapeとコピーだけで済みます。

The tricky part is step, the row stride in bytes. A publisher may pad rows, so step is not always width × 3, and some publishers leave it at 0. The code treats 0 as unpadded rather than dividing by it — dividing would reshape to a zero-width image and fail much later with an error about something else entirely. It then validates that the stride is a whole number of pixels and that the buffer is long enough, slices off the padding, and copies so OpenCV receives a writable contiguous array.

難しいのは、バイト単位の行ストライドであるstepです。publisherは行をパディングすることがあるため、stepが常にwidth × 3とは限らず、0のままにするpublisherもあります。 コードは0で割らず、0を「パディングなし」として扱います。割り算をすると幅0の画像にreshapeされ、ずっと後でまったく別の原因に見えるエラーで失敗するからです。 続いて、ストライドがピクセル数の整数倍であることとバッファ長が足りていることを検証し、パディングを切り落とし、OpenCVが書き込み可能な連続配列を受け取れるようにコピーします。

The reasoning, stated honestly in the sourceソースコードに正直に書かれた理由

The trigger was a NumPy 2 incompatibility, but that error will not appear on a stock Humble install, whose system NumPy is 1.x — so it is not the justification. The justification is that the workspace no longer carries a compiled dependency, or a workspace-wide version pin, that it does not need. The file's own docstring says cv_bridge should come back the moment a real camera does, because most drivers publish rgb8 and RealSense depth is 16UC1.

きっかけはNumPy 2との非互換でした。ただし、システムのNumPyが1.xである標準のHumble環境ではこのエラーは出ないため、それは正当な理由になりません。 本当の理由は、不要なコンパイル済み依存や、ワークスペース全体のバージョン固定を持たずに済むことです。ファイル自身のdocstringにも、実カメラを使う時点でcv_bridgeに戻すべきだと書かれています。多くのドライバはrgb8でpublishし、RealSenseの深度は16UC1だからです。

Franka Pandaはどこにでも届くわけではありません。validatorは作業領域を円筒で近似し、4つの境界値と1つの追加ルールを適用します。

Test判定Bound範囲Reason理由
height高さ−0.05 … 0.98 mBelow the table surface or above the arm's vertical span.テーブル面より下、またはアームの上下方向の可動範囲より上。

Rejections are logged with a reason string rather than silently dropped, and the surviving points are republished as a PoseArray with identity orientation — the validator has an opinion about where, not about how. このnodeをPythonではなくC++で書いたのには明確な理由があります。10 Hzのカメラフレームごとに実行されるため、コントローラを待たせる原因になってはならないからです。 また、実際のROS 2システムがそうであるように、複数言語が混在するワークスペースを示すのにも自然な場所です。

The motion half, step by step動作計画側の詳細

How a validated coordinate becomes a grasp: pose construction, Cartesian planning, the fallback, and the state machine.

検証済みの座標が把持動作になるまで。poseの構築、Cartesian計画、fallback、そしてstate machineです。

The state machine状態遷移（state machine）

IDLE→ GRASPING→ PLACING→ next ball…次のボール…→ DONE on failure →失敗時 → HOMING · ERROR

Five real states plus a fatal one. The loop lives in a while inside _run(), not in recursion — a recursive state machine that runs for seven balls and several retries would grow a stack frame per transition for no reason.

実質的な状態が5つと、致命的エラーの状態が1つです。ループは再帰ではなく_run()内のwhileで回しています。再帰で書いたstate machineを7個のボールと数回のリトライ分走らせると、遷移のたびに無意味にスタックフレームが積み上がるためです。

Each cycle: wait for a validated target that maps to a ball still on the table (with an eight-second grace period, after which any remaining unreachable balls are reported and the run ends cleanly), build the three grasp poses, show a "ghost" marker, remove the collision ball, move, place, repeat.

1サイクルの流れは次のとおりです。まだテーブル上にあるボールに対応する検証済みの対象を待ちます（8秒の猶予があり、それを過ぎると残った届かないボールを報告して正常終了します）。 次に3つのgrasp poseを作り、「ゴースト」markerを表示し、衝突判定用のボールを削除し、移動し、配置し、これを繰り返します。

The ghost-ball trickゴーストボールの工夫

There is a genuine conflict here. MoveIt refuses to plan a path that ends inside a collision object — and the grasp pose is, by definition, at the ball. Attaching the ball to the gripper (AttachedCollisionObject, the textbook answer) was tried and caused self-collision failures against panda_link7 plus a green sphere artefact stuck to the gripper.

ここには本質的な矛盾があります。MoveItはcollision objectの内部で終わる経路を計画しません。しかしgrasp poseは、定義上ボールの位置にあります。 教科書どおりの答えであるボールをグリッパーに取り付ける方法（AttachedCollisionObject）も試しましたが、panda_link7との自己干渉で失敗し、さらにグリッパーに緑の球が貼り付いて表示される不具合も出ました。

The solution splits the ball into two things. The collision ball is removed just before the approach so the planner has a clear goal. A visual ball — an RViz Marker, which has no physics and no collision meaning — is shown in the same place so the operator still sees it during the approach, then deleted the instant the gripper arrives. After the place motion succeeds, a fresh collision sphere is added inside the box. The result on screen is what a viewer expects, and the planner never fights an obstacle that is about to be picked up.

解決策は、ボールを2つに分けることです。衝突判定用のボールはアプローチ直前に削除し、プランナが障害物のないゴールを得られるようにします。 同じ位置には表示用のボール（物理も衝突判定も持たないRVizのMarker）を出しておき、オペレータがアプローチ中もボールを確認できるようにし、グリッパーが到着した瞬間に削除します。 配置動作が成功したら、箱の中に新しい衝突判定用の球を追加します。画面上は見る人の期待どおりになり、プランナがこれから拾う障害物と競合することもありません。

Cartesian first, OMPL secondまずCartesian、次にOMPL

Two ways to get the gripper from A to B:

グリッパーをAからBへ動かす方法は2つあります。

Cartesian path
Service /compute_cartesian_path. Interpolates the end-effector along a straight line in 1 cm steps and solves inverse kinematics at each one. Predictable, human-legible motion — glide over the ball, straight down; straight up, across to the box. Returns a fraction: how much of the requested path it actually managed. Below 0.95 the result is rejected.
service /compute_cartesian_path。エンドエフェクタを1 cm刻みで直線補間し、各点で逆運動学を解きます。 ボールの上まで滑らかに移動して真下へ、真上に上げて箱へ、と予測しやすく人が読み取れる動きになります。要求した経路のうち実際に達成できた割合をfractionとして返し、0.95未満なら結果を棄却します。
OMPL RRTConnect
Action /move_action. A sampling-based planner that finds some collision-free path through joint space. It will always find one if it exists, but the path can include large, alarming wrist excursions because nothing in the objective asks for a tidy route. Used only as a fallback.
action /move_action。関節空間内で衝突のない経路を何かしら見つけるサンプリングベースのプランナです。経路が存在すれば必ず見つけますが、目的関数に整った経路を求める項がないため、手首が大きく危なっかしく振れる経路になることがあります。fallback専用です。

The controller tries Cartesian, and on failure falls back with the same target expressed as a constrained OMPL goal. That ordering is why the demo looks deliberate rather than chaotic.

コントローラはまずCartesianを試し、失敗したら同じ対象を制約付きのOMPLゴールとして表現してfallbackします。デモの動きが無秩序ではなく意図的に見えるのは、この順序のおかげです。

Retiming the trajectory afterwards計画後の軌道のretiming

The OMPL path lets you request max_velocity_scaling_factor. Humble's GetCartesianPath service has no such field — it returns a trajectory timed at full speed. So the code stretches the timing after planning:

OMPLの経路ではmax_velocity_scaling_factorを指定できます。しかしHumbleのGetCartesianPath serviceにはこのフィールドがなく、全速の時間配分で軌道を返します。 そこで、計画後にコード側で時間を引き伸ばします。

t_new       = t_old / scale
velocities  ×= scale
accelerations ×= scale²

With cartesian_speed_scale = 0.5 everything takes twice as long. The acceleration term is squared because acceleration has units of distance per time squared — scaling only the velocities would hand the controller a trajectory whose numbers contradict each other, and a well-behaved controller will reject it.

cartesian_speed_scale = 0.5なら、すべての動作に2倍の時間がかかります。加速度の項が2乗になるのは、加速度の単位が距離÷時間の2乗だからです。 速度だけをスケールすると、数値同士が矛盾した軌道をコントローラに渡すことになり、まともなコントローラはそれを拒否します。

The goal constraintsゴールの制約

An OMPL goal is not a pose, it is a set of constraints. The controller builds two:

OMPLのゴールはposeではなく、制約の集合です。コントローラは2つの制約を作ります。

  • Position — a box-shaped region 4 cm on a side for a grasp, 6 cm for a place, centred on the target, attached to link panda_link8. A tolerance region rather than a point, because demanding an exact pose from a 7-axis arm makes the IK solver work far harder for no benefit.
  • Orientation — tilt tolerance 0.25 rad on the x and y axes so the gripper stays pointing down, but 3.14 rad on z, which is to say free. A sphere looks identical from every angle of wrist rotation, so constraining that rotation only removes solutions the planner could have used.
  • 位置：対象を中心とする箱形の領域で、一辺は把持時4 cm、配置時6 cm。リンクpanda_link8に対して設定します。 点ではなく許容領域にしているのは、7軸アームに厳密なposeを要求すると、IKソルバの負担が大きく増えるだけで利点がないためです。
  • 姿勢：グリッパーが下を向いたままになるよう、x軸とy軸の傾き許容値は0.25 radですが、z軸は3.14 rad、つまり自由です。 球は手首をどの角度に回しても同じに見えるため、その回転を制約しても、プランナが使えたはずの解を減らすだけです。

All grasps use yaw = 0° so the wrist keeps the same orientation from grasp to place to the next grasp, which gives OMPL simpler joint-space paths to find.

すべての把持でyaw = 0°を使うため、把持から配置、次の把持まで手首の向きが変わりません。そのぶん、OMPLが探す関節空間の経路も単純になります。

Making an asynchronous action look synchronous非同期のactionを同期的に見せる

ROS 2 actions are two-stage and callback-driven: send a goal, get a handle telling you whether it was accepted, then register another callback for the result. Written literally, a five-step pick sequence becomes five levels of nested callbacks. _send_goal() collapses that using a threading.Event and a one-element list to smuggle the result out of the closure, then blocks with a 60-second timeout. The state machine reads as straight-line code.

ROS 2のactionは2段階のcallback駆動です。goalを送ると受理されたかを示すhandleが返り、さらに結果用のcallbackを登録します。 そのまま書くと、5ステップのpick処理は5段にネストしたcallbackになります。_send_goal()はthreading.Eventと要素1つのリストを使ってclosureの外へ結果を持ち出し、60秒のタイムアウト付きでブロックすることで、これを平坦にしています。 その結果、state machineは上から順に読めるコードになります。

This only works because the node spins on a MultiThreadedExecutor with the action clients in a ReentrantCallbackGroup, and because the pick loop runs on its own thread. On a single-threaded executor the blocking wait would prevent the very callback it is waiting for from ever running — a classic ROS 2 deadlock.

これが成り立つのは、nodeをMultiThreadedExecutorでspinし、action clientをReentrantCallbackGroupに入れ、さらにpickループを専用スレッドで回しているからです。 シングルスレッドのexecutorでは、ブロッキング待ちが、待っているcallbackそのものの実行を妨げてしまいます。ROS 2の典型的なデッドロックです。

What this does not demonstrateこのプロジェクトが示していないこと

The limits of a mock-hardware, synthetic-image system, stated plainly.

mock hardwareと合成画像で構成したシステムの限界を、はっきり書いておきます。

Stating the boundary is part of the work. The following are true and are not hidden in the repository either.

限界を明記することも仕事のうちです。以下はすべて事実であり、リポジトリでも隠していません。

  • センサーのリアリティがない。画像は撮影ではなく描画したものです。ノイズ、ブラー、露出の変化、影、レンズ歪みはありません。 ここでHSVの閾値処理が成功するのは、意図的に問題を簡単にしたからです。実カメラでは真っ先に破綻する部分です。
  • 深度がない。位置は計測ではなく平面の仮定から求めています。ボールを2個積むと、上のボールは誤った位置に、確信を持って報告されます。
  • 物理がない。mock_componentsは指令された値をそのまま返します。重力も接触もグリッパーの把持力もありません。 「把持」はアームが到達するposeにすぎず、ボールはscene managerによって箱の中へ瞬間移動させています。
  • 学習ベースの要素がない。閾値処理、輪郭、モーメント、ピンホール幾何、サンプリングベースの計画と、すべて古典的な手法です。 無地のテーブル上の赤い球を検出するには、それが工学的に正しい選択です。ただし、このプロジェクト自体は学習済みモデルを示すものではありません。
  • 到達可能性のモデルは円筒です。Pandaの実際の作業領域は、姿勢によって境界が変わる複雑な形状です。円筒は保守的な近似であり、近似であることを明記しています。
  • パッケージ内のREADMEは古いままで、削除済みの版のシステムを説明しています。実際にビルドされるものを反映しているのは、ルートのREADMEだけです。
  • No sensor realism. The images are drawn, not captured. No noise, no blur, no exposure variation, no shadows, no lens distortion. HSV thresholding succeeds here because the problem was made easy on purpose; on a real camera it would be the first thing to break.
  • No depth. Positions come from a plane assumption, not from measurement. Stack two balls and the upper one is reported at the wrong place with full confidence.
  • No physics. mock_components reports back whatever it is commanded. There is no gravity, no contact, no gripper force — the "grasp" is a pose the arm reaches, and the ball is teleported into the box by the scene manager.
  • No learned component. Everything is classical: thresholding, contours, moments, pinhole geometry, sampling-based planning. That is the correct engineering choice for detecting red spheres on a plain table, and it means this project does not itself demonstrate a trained model.
  • The reachability model is a cylinder, not the Panda's actual workspace, which is a complicated shape with orientation-dependent boundaries. It is a conservative approximation and is labelled as one.
  • The inner package README is out of date and describes a deleted version of the system. Only the root README tracks what is actually built.
The stated next steps明記している次のステップ

Swap mock_components for Gazebo Ignition with a Panda plugin — the perception and planning stack needs no changes. Then add a learned component where the problem is genuinely hard — grasp pose and orientation prediction for non-spherical objects — and export it to ONNX and TensorRT for a Jetson. Detection stays HSV; a neural network for red spheres would be the wrong tool.

mock_componentsを、Pandaプラグイン付きのGazebo Ignitionに置き換えます。認識と計画の部分は変更不要です。 次に、本当に難しい問題である非球形物体のgrasp poseと姿勢の予測に学習ベースの要素を加え、Jetson向けにONNXとTensorRTへexportします。 検出はHSVのままにします。赤い球の検出にニューラルネットワークを使うのは、道具の選び方として誤りです。

The short versionまとめ

The whole project compressed into one paragraph.

プロジェクト全体を1段落にまとめます。

A two-package ROS 2 Humble workspace in which a Franka Panda clears seven balls into a box using only what a camera saw. A Python node renders a synthetic 640×480 top-down frame; a second Python node finds the balls by HSV thresholding and recovers their table-plane positions by exact pinhole back-projection; a C++ node filters those positions against the arm's reachable cylinder; a Python state machine picks up only what survived, preferring straight-line Cartesian motion and falling back to OMPL, retiming the Cartesian trajectory by hand because Humble's service does not expose velocity scaling. Every tunable number lives in two YAML files. The one file that reimplements a standard library carries fifteen contract tests. The simulation boundary — drawn images, a plane assumption, mock hardware — is documented rather than implied.

2つのパッケージからなるROS 2 Humbleのワークスペースで、Franka Pandaがカメラで見たものだけを頼りに7個のボールを箱へ片付けます。 Pythonのnodeが真上から見た640×480の合成フレームを描画し、2つ目のPython nodeがHSVの閾値処理でボールを見つけ、厳密なピンホールback-projectionでテーブル平面上の位置を復元します。 C++のnodeがその位置をアームの到達可能な円筒と照合してフィルタし、Pythonのstate machineが残ったものだけを拾います。動作は直線的なCartesian動作を優先し、失敗時はOMPLにfallbackします。 HumbleのserviceがCartesian軌道の速度スケーリングを提供していないため、軌道のretimingは自前で行っています。調整可能な数値はすべて2つのYAMLファイルにあります。 標準ライブラリを再実装した唯一のファイルには、15個の契約テストがあります。シミュレーションの境界（描画画像、平面の仮定、mock hardware）は、暗黙の前提にせず明記しています。
