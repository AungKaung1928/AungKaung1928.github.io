A C++ Environment That Matches Python to the Bit

The Microduck project trains a balance policy in a Python MuJoCo environment that runs eight forked processes on a laptop. This repo is that environment again in C++17, on threads instead of processes, with a Python binding so the same training script runs on it unchanged. The claim it makes is not "faster". It is that the two environments produce the same 48 numbers, the same reward and the same flags at every step, to the last bit, and that a test proves it on every commit. The speed was measured afterwards.

01

In plain words

What a vector environment is, why this one is written in C++, and what "bit-identical" buys.

Reinforcement learning trains a policy by letting it act in a simulator millions of times. To do that quickly you run many copies of the simulated robot at once and feed the policy a batch of observations per step. The object that holds those copies and steps them together is called a vector environment.

The Microduck project has one written in Python. Python can only execute one thread of its own code at a time, so its vector environment starts eight separate processes and talks to them through pipes. That works, and every number in that project was measured on it. It also means a fixed cost per step that has nothing to do with physics: serialising actions, waking eight processes, waiting for the slowest one, copying observations back.

This repository is the same environment in C++. The step loop has no interpreter in it, so eight environments run on eight threads of one process and share memory. A small binding lets Python call it, and the Microduck training script runs on it with no edits.

The one claim

A faster environment that behaves even slightly differently trains a different policy, and then nothing measured on the Python environment carries over. So the first thing tested, before any timing, is equality: given the same starting state and the same actions, the C++ environment returns the same 48 floating-point observations, the same reward and the same flags as the Python one, with no tolerance. Over 25 episodes and 6,275 observations there is not one differing bit. That test runs in CI against a pinned commit of the Python repository.

Getting there meant matching how numpy adds fourteen numbers, how Python squares a float, and how a float32 constant is promoted to float64. Those three details are the middle of this page. The throughput numbers are at the end, with their caveats, because they turned out to say something about the Python environment too.

Terms used on this page

vector environmentN simulated robots stepped together so the policy sees a batch of N observations per step. The Python one uses N processes; this one uses T threads.
thread vs processThreads share one address space and cost nothing to exchange data. Processes have separate memory and exchange data through pipes, which costs a copy and a context switch each way.
bit-identicalTwo floating-point numbers with exactly the same 32 or 64 bits. Stricter than "close": no tolerance, no rounding allowed.
pybind11A header-only library for exposing C++ classes to Python. Here it wraps Env, VecEnv and the config structs, and passes numpy arrays without copying.
PCG64The random number generator numpy uses by default. Reimplemented here so the C++ side draws from the same family; the seeding differs on purpose (see section 04).
domain randomisationChanging physical parameters (servo gains, masses, friction, latency) each episode so the policy does not overfit one exact model. Here it writes into the model, which is why each environment owns its own copy.
sanitizerA compiler mode that instruments the binary to catch memory errors (AddressSanitizer), undefined behaviour (UBSan) or data races between threads (ThreadSanitizer) at run time.
burst vs sustainedA 20-second measurement on a cool laptop reads high because the chip is still at turbo. A six-minute run with no pause shows the rate the power limit allows. Budgets come from the second.
reference windowA single-thread measurement taken before the sweep and after every row. If it moves, the machine changed state mid-sweep and the rows are not comparable.
env-steps/sEnvironment steps per second, summed over all environments. One env step here is 10 physics steps plus observation, reward and bookkeeping.
02

Why it exists

Two open questions from the Python project, and the rule that equality comes before speed.

The Python project left two measurements it could not explain from inside Python. First, its environment wrapper cost 25% over bare physics on one core. Second, scaling across eight processes settled at 55% efficiency on one robot model and 42% on the one actually used for training, and the loss was attributed to a shared resource outside the cores, without proof. Whether process isolation itself was part of the loss was unknowable without an implementation that did not use processes.

A C++ version answers both, but only if it is the same environment. The order of work therefore was: port the environment, prove equality, and only then run the benchmarks. Timing code that has not been proven equal produces a number about a different environment.

Python, per stepPickle 8 action rows, write to 8 pipes, each worker unpickles, steps, pickles obs, writes back, parent reads 8 pipes and stacks.
C++, per stepWrite the action batch into shared memory, bump an atomic counter, 8 threads step their environments, caller reads the observation buffer.
Same in both10 × mj_step, one mj_forward, 48-dim observation, reward terms, three seeded pushes, fixed 250-step episodes, autoreset.

Everything measured in the Python project was measured inside a budget of eight of the machine's fourteen cores. This repo inherits that rule in code: VecEnv refuses more than eight threads unless the caller passes allow_overcommit.

04

How the equality test works

Python draws the randomness, C++ replays it, and everything that comes back is compared with no tolerance.

The Python environment gets its randomness from numpy: initial joint noise, then which control steps the pushes land on (a draw without replacement), their speeds and directions, and under domain randomisation the servo parameters, mass, friction, latency and noise. Reproducing that draw in C++ would mean reimplementing numpy's seed-sequence expansion, its choice and its ziggurat normal sampler, and getting all three right. It is possible. It is also beside the point, because the draw is not what the environment does; it is what the environment is handed.

So the test runs the Python environment, reads what it drew, and passes those values to the C++ environment through EpisodeParams: the post-noise joint state, the push schedule, and the DR factors if any. From that moment the two environments share every line of logic and receive the same 250 actions.

pe = MicroduckEnv(seed=s, **kw); o_py = pe.reset(seed=s)
params = vecenv_cpp.episode_params(pe.data.qpos[qi], pe.data.qvel[vi],
                                   pe._push_at, pe._push_vel, dr=pe.dr.current)
ce = vecenv_cpp.Env(make_config(**kw), s); o_cpp = ce.reset(params)
# 250 identical actions into both; compare obs, reward, terms, flags, info

Env::reset(const EpisodeParams&) is that entry point. Env::reset() with no argument uses the environment's own PCG64 and is what training uses.

The 25 episodes cover both reward versions, action latency 0 and 2, initial noise 0 and 0.02, an action scale of 0.5 with five pushes, the two held-out physics variants (35 and 25 position coordinates, with strided joint indices), and two DR cases with injected factors. Every observation is the same float32 array, every reward the same float64, and pushed, fallen, t, truncated, terminated, trunk_height and upright_cos agree on every step. The pytest suite asserts this at 1e-6 on observations and 1e-9 relative on rewards, so a last-bit difference in a system library would pass while a real defect would not; the report script counts exact matches separately so the distinction stays visible. One further test shifts a single push by one step and checks that the comparison notices.

Deliberately different

Env(cfg, seed=7) and MicroduckEnv(seed=7) draw different pushes. The C++ seeds PCG64 from a 64-bit integer through splitmix; numpy runs SeedSequence. The PCG64 core stream and its uniform() are numpy's exactly (a test hands numpy's internal state to the C++ class and checks 1,000 outputs of each), but normal() is Marsaglia polar, not the ziggurat, and integers() uses a different rejection scheme. A Python run and a C++ run with the same seed are two samples of the same distribution, not a replay. Compare them across seeds.

05

Three arithmetic details, and one about the solver

What was actually different the first time the two environments disagreed in the last bit, and how each was found.

01

numpy does not add fourteen numbers left to right

The reward takes np.mean over the fourteen joints. For arrays of 8 to 128 elements numpy's reduction keeps eight partial sums and combines them as a tree. Measured on 20,000 random 14-vectors: a sequential loop matched np.mean on 15,831; a tree starting from the identity 0 matched on 20,000 of 20,000; a tree starting from the first element matched on 11,776. np::pairwise_sum is the first of those, copied from numpy's own loop structure. A C++ test feeds it an input where the two orders provably differ: {1e16, 1×7, -1e16, 0×5} sums to 0 sequentially and to 6 as a tree.

02

Python's x ** 2 is pow(x, 2.0), not x * x

Python routes a float power through the C library's pow. Measured on 2,000,000 random doubles, pow(x, 2.0) and x * x differ in 1,621 of them. The v1 height term uses the power operator. GCC folds pow(x, 2.0) into a multiply unless stopped, so np::py_pow passes the exponent through a volatile to force the library call.

03

The observation scale is float32, the raw values are float64

The Python side multiplies a float64 array by a float32 constant table. numpy promotes the constant, so the product is raw * double(float32(0.05)), and double(0.05f) is 0.05000000074505806, not 0.05. The C++ scale table is built from the float32 literals and widened the same way.

04

A second mj_forward is not a no-op

The Python reset calls mj_forward once on the keyframe and a second time only after applying initial noise. Running the forward pass twice on an unchanged state lands a few units in the last place elsewhere, because the constraint solver warm-starts from the previous acceleration. The C++ reset runs the second pass under exactly the same condition, init_noise > 0.

The build also sets -ffp-contract=off and -fno-fast-math. A fused multiply-add rounds once where numpy rounds twice, and one fused instruction anywhere in the reward would have broken the table above.

06

Threading design

One model per environment, a fixed thread assignment so results never depend on the thread count, and a wake-up scheme that costs nothing when idle.

one model per env
Domain randomisation writes into mjModel (damping, gains, masses, friction). A shared model would make DR a data race and every environment identical. Env takes a prototype and mj_copyModels it. A test mutates one environment's masses and checks the prototype and its neighbours are untouched. Sixteen bodies and 82 geoms: the copies are kilobytes.
env i on thread i mod T
Always. So the assignment of environments to threads is fixed, and the result does not depend on T. A test runs the same 300 steps on 1, 2 and 4 threads and compares observations, rewards, dones and terminal observations with ==; another runs 260 steps as three sequential Envs, autoreset included, and gets the same bits.
generation counter
The caller writes the action batch, increments an atomic counter and works as thread 0. The other T−1 threads spin on the counter for tens of microseconds and then block on a condition variable. While the policy is computing its next action the pool burns nothing; while it is stepping, there is no futex call per step. Acquire and release ordering on the counter and on the completion count is what makes the action and observation buffers visible without a lock.
autoreset
Matches the Python version: when an episode ends, the observation returned is the new episode's first, and the ended episode's final observation is kept in terminal_obs. Every episode here ends on the step limit, never on a terminal state, so the training loop bootstraps V(terminal_obs); the flags are carried so a stock advantage estimator cannot get this wrong silently.
the budget
More than eight threads is refused unless the caller says allow_overcommit. Every number in the Python project was taken inside eight of fourteen cores on a laptop with other work to do, and this repo inherits that as a constructor check rather than a comment.
07

Sanitizers and CI

Three CI jobs, and two things about MuJoCo's prebuilt library that had to be worked around to run them.

CI runs three jobs on every push. The first builds Release, runs the 34 C++ cases, the 41 Python tests and the equality report against the Python repository at a pinned commit, after fetching the robot assets from their upstream (they are Creative Commons BY-SA-NC and are never committed). The second and third rebuild the C++ suite under -fsanitize=address,undefined and under -fsanitize=thread. The thread-count independence test is the one ThreadSanitizer exists for: a race on the shared action or observation buffers would fail the build.

01

mujoco.h does not compile under AddressSanitizer in C++

MuJoCo's header includes mjsan.h, written for building MuJoCo itself under ASan. When the compiler defines __SANITIZE_ADDRESS__ it declares inline helpers with an attribute syntax g++ rejects in a C++ translation unit. This repo links the prebuilt, uninstrumented library and never touches those helpers, so include/vecenv/mujoco.hpp predefines the header's include guard and two stub macros, and every file includes MuJoCo through that one wrapper.

02

MuJoCo's XML compiler has its own thread pool

mj_loadXML spawns a pool inside the prebuilt library. ThreadSanitizer cannot see the synchronisation inside code it did not instrument, so it reports the pool's internal mutex as a race. tests/cpp/tsan.supp contains one line, race:libmujoco, and nothing this repo compiles is suppressed. On recent kernels TSan also aborts on an unexpected memory mapping; setarch $(uname -m) -R disables address-space randomisation for that one process without privileges, and CI lowers vm.mmap_rnd_bits on the runner instead.

The C++ side links the same libmujoco.so that the Python side imports: CMake asks the Python interpreter where the wheel lives and takes the headers and library from there, so nothing is installed system-wide. check_library_version() refuses to run if the header and the library disagree. The equality claim is only meaningful against the same physics binary.

Measured throughput

Four measurements taken on 2026-09-22 on the same laptop, each with the guard verdict its own tool printed.

The protocol is the Python project's. A sweep runs 1, 2, 4 and 8 threads for 20 seconds each, with a single-thread reference window before the sweep and after every row. The JSON is marked unstable if a reference drifts more than 10% and trending if the reference moves in one direction across three windows by more than 4%. A sustained run holds 8 threads for 18 windows of 20 seconds with no pause. All runs were under nice -n 10, eight of fourteen cores, no other work on the machine.

Guard verdict, and what it means here

Taken at 21:03, machine rebooted minutes before. A first sweep just before it read 5,390 / 10,823 / 19,956 / 27,087, so every row reproduced within 1%. The guard nevertheless marked both sweeps trending: the single-thread reference rose 4.4% across three consecutive windows against a 4% bar. On this laptop the single-thread reference scatters about 5% from one window to the next, so the trend detector fires on scatter. A third sweep started immediately afterwards, with the package still warm, read 5,340 / 10,496 / 18,909 / 24,384: 10% lower at 8 threads. That is the chained-benchmark effect the Python project already documented, and it is why the second sweep, not the third, is the table.

One thing the two sweeps cannot tell you: the bare 1-thread row, 5,404, is below the full-environment 1-thread row, 5,639, taken six hours earlier. Physics alone cannot be slower than physics plus observation, so the two sweeps were taken in different host power states. The host's power mode is not visible from inside the guest, and the env-to-bare gap cannot be read from these two tables to better than about 4%. Both tables are individually consistent; the comparison between them is not.

Two conclusions

The README set a decision rule before the run: under 1.3× at 8 workers, the C++ environment is not worth its build step for training. At 1.9× to 2.0× it clears the rule.

The second conclusion is about the Python project. Its vector environment at 8 processes delivers about 6,400 env-steps/s in this driver, half of the 13,300 that project budgeted from bare physics times a measured wrapper factor. The inter-process round trip, pickling actions out and observations back through eight pipes each step, was never in that composition. The training script itself logs its rate every update, and that figure, not any composed one, is the number to budget from.

Not yet run: the Python project's PPO on this backend. scripts/ppo_cpp.py exists and a 1,024-step smoke of it wrote a checkpoint, which proves the plumbing and nothing else. Return curves and wall-clock for the 50M-step budget on both backends are the open item.

09

What it does not prove

The boundaries of the equality claim and of the speed numbers, stated so they are not read past.

  • Bit equality holds on one machine, one compiler, one C library. Python's pow and exp and the C++ ones are the same library calls on the same host, which is why they agree. A runner with a different glibc, or a numpy built with a different vectorised exp, could differ in the last bit on the height term. The test tolerances are set so that would pass and a real defect would not.
  • The draw is not replicated. Same seed, different pushes. A step-by-step replay of a Python training run on the C++ backend is not available; comparisons between the two are statistical, across seeds.
  • Sensor noise is not contract-tested, for the same reason: it is a Gaussian per step and the C++ draws its own. The contract cases run with it off.
  • No policy has trained on this yet. The smoke run proves the training script executes against it, not that a policy trained here matches one trained on the Python environment.
  • One robot. Env is Microduck-shaped: 14 actuators, a standing keyframe, a named trunk body, named gyro and orientation sensors. The threading layer is not, and a second model behind the same interface is the natural next step.
  • No rendering. Image observations through MuJoCo's C rendering API are deferred until a machine with a working EGL context exists; the laptop this was written on has GLFW through WSLg and nothing else.
  • The speed numbers are for this laptop. Fourteen cores of three kinds under a hypervisor, with a power state the guest cannot read. The ratios are more portable than the absolute rates, and the sustained band is more portable than any 20-second row.

The short version

The whole project in one paragraph.

The Microduck balance task has a Python environment that runs eight forked processes. This is the same environment in C++17 on eight threads, with a pybind11 binding and a drop-in class so the Python training script runs on it unchanged. Before any timing, the two were made to agree to the bit: the test lets Python draw the episode's randomness and hands the drawn values to the C++ side, then feeds both 250 identical actions and compares everything that comes back with no tolerance. Reaching 6,275 of 6,275 identical observations took matching numpy's eight-accumulator summation tree, routing Python's power operator through the C library's pow behind a volatile, widening a float32 scale table the way numpy does, and running MuJoCo's forward pass a second time only under the same condition the Python code does, because the solver warm-starts. CI runs that comparison against a pinned commit of the Python repository, and rebuilds the C++ suite under AddressSanitizer and ThreadSanitizer, each of which needed a workaround for MuJoCo's prebuilt library. Measured afterwards on the same laptop: the full environment runs 20,287 env-steps/s in a 20-second burst at eight threads and settles between 13,300 and 16,200 over six minutes, with the same power-management curve the Python version shows; head to head under identical random actions the C++ threads deliver 1.9 to 2.0 times the Python processes at eight workers, above the 1.3× the README had set as the threshold for being worth the build. The same comparison showed the Python vector environment delivering about half the rate its project had budgeted from physics alone, because the inter-process round trip had never been in that composition. Thread efficiency at eight workers, 45%, matched the Python processes' 42%, so process isolation was not the scaling loss; the chip is. A policy has not yet been trained on this backend.
